# double-float + ネイティブFP64 同時実行の検証結果 (GH200/H100)

- 日付: 2026-07-24
- GPU: NVIDIA GH200 120GB (Hopper, sm_90, 132 SM), CUDA 13.2, driver 595.58.03
- コード: `df_concurrent_h100.cu` (デモ本体), `probe_starve_h100.cu` (原因切り分けプローブ)
- 前提知見: `RESULTS_prelim_h100.md` (FFMA/DFMAは共存可だがGH200では恩恵が小さい。SM内共存率は100%)

## ストーリーの検証結果: **Blackwellとは逆に「DFエミュレーションを使う動機がない」**

| 構成 | FP64相当スループット |
|---|---|
| ネイティブFP64のみ | 31.428 TFLOPS |
| DFエミュレーションのみ (最良、2acc版) | 3.377 TFLOPS相当 (ネイティブの **0.11倍**、約1/9) |
| 同時実行 最良 (DF 8acc + FP64) | 18.802 TFLOPS相当 (ネイティブ単独比 **0.60倍**) |
| 参考: 単純合算の理論上限 (3.38+31.43) | 34.81 TFLOPS相当 (実際には到達しない) |

- DF演算の実装・精度検証はBlackwell版と同一コード: DF誤差1.25e-13、素のFP32誤差5.524e-6、通常版/全FMA版のビット不一致0/4096系列 (GPUに依らず数式が同一であることの確認)。
- **重要: GH200ではネイティブFP64がDFエミュレーションの約9倍速い。** Blackwellでは逆にDFエミュレーションがネイティブFP64の4.0倍速かった (FP64演算器が1/64に縮退していたため)。GH200/H100はFP64演算器が縮退していない (1:1.65) ため、DFエミュレーションを使う実用上の動機自体がそもそも存在しない。

## 2ストリーム同時実行の3構成 (それぞれDF側/FP64側/合算)

| 構成 | DF側 [TFLOPS相当] (保持率) | FP64側 [TFLOPS] (重複中保持率) | 合算 [TFLOPS相当] |
|---|---|---|---|
| (a) 通常版・8アキュムレータ (発行飽和) | 1.736 (57.3%) | 17.07 (54.3%) | **18.80** |
| (b) 全FMA版・8アキュムレータ (発行飽和/全FFMA) | 1.691 (65.9%) | 13.50 (43.0%) | 15.19 |
| (c) 通常版・2アキュムレータ (発行に隙間あり) | 2.138 (63.3%) | 14.66 (46.6%) | 16.80 |

**すべての構成で合算 (15.2–18.8 TFLOPS相当) はネイティブFP64単独 (31.43 TFLOPS) を大きく下回る。** すなわち、DFエミュレーションを同時実行すると、ネイティブFP64単独より **最大47%も遅くなる**。Blackwellで最良だった「発行に隙間を作る」(c)構成は、GH200では最良ではなく、素朴な(a)構成 (8アキュムレータ・発行飽和) が最も合算スループットが高いという逆転も見られた。

## 命令種別プローブ (`probe_starve_h100.cu`, FP64側1024thr/SM=32ワープ)

| 競合ストリーム (256thr/SM) | 重複区間中のFP64保持率 |
|---|---|
| FFMA連続 (発行飽和) | **20.3%** |
| FADD連続 (発行飽和) | 0.4% |
| FMUL連続 (発行飽和) | 0.1% |
| MUL/ADD交互 (発行飽和) | 0.3% |
| DF通常版 8acc (78%がADD/SUB系, 発行飽和) | **54.1%** |
| DF全FMA版 | 51.0% |
| FADD低密度 (発行率~50%) | 67.9% |

512thr/SM (16ワープ) でもほぼ同一の値 (FFMA 20.1%, FADD 0.2%, FMUL 0.2%, MUL/ADD 0.3%, DF通常版54.0%, DF全FMA版50.9%, FADD低密度67.9%)。

### Blackwellと共通する点

- **FADD/FMUL単体の発行飽和ループはDFMAをほぼ完全に停止させる** (0.1–0.4%)。この「FADD/FMUL vs DFMAの発行競合」という機構自体はHopperにも存在する。

### Blackwellと異なる新知見

1. **FFMA連続列でもGH200では重複中20%程度まで低下する。** Blackwellでは94.8%保持でほぼ無競合だった。FP64が1:2に近いレートで頻繁に発行スロットを要求するため、FFMAが発行スロットを100%使っていても無視できない競合が生じると考えられる (Blackwellでは1/64しか要求しないため実質無競合だった)。
2. **DF演算 (命令構成の78%がFADD/FSUB) そのものは、単純なFADD/FMULループほど強くDFMAを阻害しない** (54%保持 vs 単純FADD/FMULの0.1–0.4%)。Blackwellでは逆に「DF通常版は単純FADD/FMULとほぼ同じ0.5%まで枯渇する」という結果だった。命令スケジューリング(制御ビット)のコード生成依存性は元論文(`sec:allfma`, 可搬性の限界)でも指摘されていた通りで、この非対称性は世代・コンパイラ間でそのまま転移しない。

## 実用への示唆 (GH200/H100版まとめ)

1. **FP64演算器が縮退していない(1:2)データセンタ系GPUでは、DFエミュレーションを使う意味自体が薄い。** ネイティブFP64が約9倍速いため、本稿の「エミュレーション+ネイティブFP64併用」構成はそもそも不要であり、素直にネイティブFP64だけを使うべきである。
2. **「発行スロット競合でFP64側が犠牲になる」という定性的機構はHopperでも観測される**が、量的な出方 (FFMA vs DF命令列の相対的な脅威度、どの構成が最良か) は世代間で反転しており、Blackwellでの数値・最適構成をそのまま外挿できない。
3. 元論文 (`paper/fp32fp64_report.tex`, `sec:issue-model`) の「データセンタ系列 (FP64:FP32=1:2) では発行スロット律速により合算がFP32単独と変わらない」という予測は、正確には**「FP32側の性能はほぼ変わらないが、FP64側が同時実行によって大きく損なわれるため、あえて併用する動機がない」**という形でGH200上で確認された。

## 再現手順

```
nvcc -O3 -arch=sm_90a -o df_concurrent_h100 df_concurrent_h100.cu && ./df_concurrent_h100
nvcc -O3 -arch=sm_90a -o probe_starve_h100 probe_starve_h100.cu && ./probe_starve_h100
```

PBS環境 (Miyabi等) では `qsub run_h100.pbs` でビルド・実行・ログ収集一式を実行できる (`results_h100/` に出力)。
