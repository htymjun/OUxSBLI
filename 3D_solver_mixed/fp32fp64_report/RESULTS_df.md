# double-float + ネイティブFP64 同時実行の検証結果

- 日付: 2026-07-23
- GPU: RTX PRO 6000 Blackwell WS (GB202, sm_120, 188 SM), CUDA 13.2
- コード: `df_concurrent.cu` (デモ本体), `probe_starve.cu` (原因切り分けプローブ)
- 前提知見: `RESULTS_prelim.md` (FFMA vs DFMA は共存可、FP64側は16+ワープ/SM必要)

## ストーリーの検証結果: **成立する。ただし条件付き (+9.2%)**

| 構成 | FP64相当スループット |
|---|---|
| ネイティブFP64のみ | 1.80 TFLOPS |
| DFエミュレーションのみ (最良) | 7.22 TFLOPS相当 (ネイティブの4.0倍) |
| **同時実行 (DF 2acc + FP64)** | **7.88 TFLOPS相当 (+9.2%)** |
| 理論上限 (7.22 + 1.80) | 9.02 TFLOPS相当 (+25%) |

- DF演算: Dekker/Knuth系、DF-FMA相当 = 18 FP32命令 (mul 7 + add 11)
- 精度: FP64参照との相対誤差 1.25e-13 (悪条件の漸化式1000回) vs 素のFP32 5.5e-6 → 「double相当」の主張は妥当
- 成功構成 (c): DF側 87.2%保持 + FP64側 96.9%保持が同時進行 (DF 256thr/SM, FP64 1024thr/SM, 2ストリーム)

## 最重要知見: DFMAはFP32命令ストリームの「発行の隙間」でしか走れない

競合カーネルの命令種・発行密度を変えた切り分け (`probe_starve.cu`) の結果:

| 競合ストリーム (256thr/SM) | 重複区間中のFP64保持率 |
|---|---|
| FFMA連続 (発行飽和) | 94-95% |
| **FADD連続 (発行飽和)** | **~0% (完全枯渇)** |
| **FMUL連続 (発行飽和)** | **~0%** |
| MUL/ADD交互 (発行飽和) | ~0% |
| DF通常版 8acc (78%がADD/SUB系, 発行飽和) | ~0% |
| DF全FMA版 (後述) | 0〜92% (コード生成依存で不安定) |
| FADD低密度 (依存チェーンで発行率~50%) | 99.6% |
| DF通常版 2acc (発行に隙間) | 94-97% |

解釈:
- FFMAとDFMAはほぼ独立に発行できる(前回知見の通り)
- **FADD/FMUL系の命令が発行スロットを埋め続けると、DFMAは一切発行されない**
  (共有ディスパッチ経路の調停でDFMAが永続的に負けると推定)。
  FP64ワープを32本に増やしても回復しない。SM内共存自体は成立している(smid確認済)
- ただし競合ストリームの発行に隙間があれば(依存チェーン律速)、DFMAはその隙間で
  ほぼフルレートに達する。DFMA飽和に必要な発行スロットは全体の1/64しかないため、
  わずかな隙間で足りる

## 全FMA化について (負の結果として重要)

`x+y → fma(x,1,y)`, `x*y → fma(x,y,0)` の変換で数値結果をビット単位で保ったまま
DF演算列を全FFMA化できる (4096系列で不一致0を確認)。ただし:

- ptxasが `fma(x,±1,y)` をFADDに強度低減するため、定数1.0/0.0はカーネル引数で渡す必要がある (SASSで要確認)
- 全FMA版の単独性能は通常版の約89% (FFMAの3オペランド化によるレジスタバンク圧と推定)
- **同時実行時の効果はコンパイル文脈依存で不安定**: 同一ソースのループでも、バイナリによって
  FP64側 92%回復 / 完全枯渇 / 逆にDF側が50%に低下、と結果が変わる (`mix_test.cu` の2x2実験)。
  発行調停が命令スケジューリング(制御ビット)レベルの詳細に敏感で、制御不能。
  → 実用手段としては推奨できない。「発行密度に隙間を作る」方が頑健

## 実用への示唆

1. **現実のDFカーネル(GEMM等)は好条件**: メモリアクセス・アドレス計算・同期などで
   発行密度は synthetic loop より低く、DFMAが入り込む隙間は自然に存在するはず。
   本検証の「発行飽和ループ」は最悪ケースであり、実カーネルでは (c) に近い挙動が期待できる
2. 上限は +25% (= ネイティブFP64/DF比)。今回 +9.2% を実測。DF側の保持率(87%)が損失の主因
3. **Ozaki方式 (INT8 Tensor Core) との併用が本命候補**: IMMAパイプはFP32パイプと別なので、
   FADD/FMUL vs DFMA のような発行調停の問題自体が生じない可能性が高い (未検証・次のステップ)

## 再現手順

```
nvcc -O3 -arch=sm_120 -o df_concurrent df_concurrent.cu && ./df_concurrent
nvcc -O3 -arch=sm_120 -o probe_starve probe_starve.cu && ./probe_starve
```
