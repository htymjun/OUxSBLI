# Simplify the viscous-kernel diffs (calc_visc2.f90.fypp ×2, calc_visc_high.f90.fypp, calc_visc_high_internal.f90.fypp)

## Context

The four currently-unstaged files (`2D_solver/src/calc_visc2.f90.fypp`, `3D_solver/src/calc_visc2.f90.fypp`, `3D_solver/src/calc_visc_high.f90.fypp`, `3D_solver/src/calc_visc_high_internal.f90.fypp`) already contain an in-progress optimization pass: it introduces `use libm` + `fma(...)` calls, wraps output stores in `__ldcg`/`__stcg`, and caches repeated array reads into named scalars. That work should stay.

But the pass over-applied itself in one specific, narrow way: in the `VISC_ORDER == 4` and default 6-point-stencil branches, it took vector-slice loads like `mu6(:) = mu(i-2:i+3,j,k)` and expanded them into 6 individual scalar assignments even where the result (`mu6`) is only ever consumed as a whole array afterwards (passed to `interp6(mu6)`, `calc_tau_straight(mu6,...)`, or used in plain array arithmetic like `Cp*T6(:)`). No `fma` is ever called on those individual elements there, so the expansion buys nothing and just triples the line count. It left the original one-line vector-slice form behind as a dead `!`-prefixed comment everywhere it did this.

**The `VISC_STENCIL == 'ME4Base'` branch is different and should be left alone.** It also expands slice-shaped formulas (`mu3(:) = 0.0625d0 * (9.d0*(...) - (...))`-style) into named scalars (`mum2, mum1, mu0, mup1, mup2, mup3`, ditto `T*`/`mut*`) plus per-element `fma(...)` calls. I initially misread this as the same kind of needless expansion and drafted a `vfma` array-wrapper to undo it — that was wrong, and per your correction it's being dropped from the plan entirely. The scalar decomposition here is genuinely worth keeping, for two reasons you flagged:
1. **Register reuse across overlapping windows**: `mu3(1)`, `mu3(2)`, `mu3(3)` are built from overlapping 3-4 element windows of the same 6-point stencil (`mum2..mup3`). Reading each of the 6 source points into a register once and reusing it (`mu0` feeds `mu3(1)` and `mu3(2)`; `mup1` feeds all three) avoids redundant device-memory traffic. An array-slice-expression version like `vfma(9.d0, mu(i-1:i+1,j,k)+mu(i:i+2,j,k), ...)` would re-read the overlapping elements (`i`, `i+1`) from DRAM redundantly instead of reusing a cached register — exactly the kind of redundant access the confirmed-good caching in `calc_visc2.f90.fypp` (rule 4 below) already avoids.
2. `fma(x,y,z)` (confirmed via `/opt/nvidia/hpc_sdk/Linux_x86_64/24.7/compilers/src/libm.f90`) is `bind(c)`, scalar `real(8), value` args only — it can't take a slice directly, so per-element scalar calls are required to fuse at all.

So the `ME4Base` branch's scalar decomposition is just another instance of rule 4 (redundant-read elimination via named scalars), not a violation of "don't delete vector loads" — there's no vector load being thrown away here for no reason; the values are reused, which is exactly why keeping them scalar is correct. **No new `vfma`/`mod_vfma` module is needed anywhere** — dropped from the plan.

The goal, simplified back to its essentials: keep every real improvement from the current diff (`fma` fusion, `__ldcg`/`__stcg`, and all redundant-read-elimination scalar caching including the `ME4Base` branch's), restore only the vector-slice loads that were needlessly thrown away in the `VISC_ORDER==4`/default-6-point branches (where the resulting array is used exactly once, whole, with no reuse and no `fma`), and delete the dead commented-out lines throughout.

## The rule to apply, uniformly, at every site touched by the current diff

1. **An array was carved out of a slice purely to repopulate it, then consumed exactly once as a whole vector, with no `fma` and no element reuse** (`mu4(:)`, `mu6(:)`, `T4(:)`, `T6(:)`, `mut4(:)`, `mut6(:)`, `qc24(:)`, `qc26(:)` in the `VISC_ORDER==4` and default 6-point-stencil branches — these only ever feed `interp4/6`, `diff4/6`, `calc_tau_straight/cross(_LES)`, or plain array addition like `Cp*T6(:)+...+qc26(:)`; and the single-use `qc2_c`/`qc2_e`/`qc2_n` scalars folded into the boundary-fallback `H(:)` array literal in `calc_visc_high.f90.fypp`) → revert straight to the original vector-slice assignment (`arr(:) = src(i-n:i+n,j,k)`), deleting the dead `!`-commented line that shows the old form (it becomes live code again).
2. **A scalar temp is read ≥2 times for redundant-read elimination**, whether from a single point (`mu_c`/`mu_e`/`mu_cjm`/.../`T_c`/`T_e`/`mut_c`/... in `calc_visc2.f90.fypp` and the boundary-fallback `else` block of `calc_visc_high.f90.fypp`) or from an overlapping-window stencil expansion (`mum2..mup3`/`Tm2..Tp3`/`mutm2..mutp3` in the `ME4Base` branches, feeding the per-element `fma`-based `mu3(1..3)`/`mut3(1..3)`/`kTx3(1..3)` (or `kTy3`/`kTz3`)) → **keep exactly as-is**.
3. **Any other leftover `!`-commented dead code** documenting a pre-transformation expression (including in the `ME4Base` branches, where rule 2 keeps the live `fma` version and the comment above it is now pure clutter) → delete the comment, nothing to restore.

Everything else added by the diff (`use libm`, all `fma(...)` fusions on scalars, the `__ldcg`/`__stcg` load-modify-store wrapping around every `E(...)`/`F(...)`/`G(...)` write) stays untouched.

## Where this applies

- **`2D_solver/src/calc_visc2.f90.fypp`, `3D_solver/src/calc_visc2.f90.fypp`**: no slice loads exist here at all (2nd-order stencil is all single-point accesses), so rule 1 never fires. The only change is deleting dead `!`-commented lines (rule 3); `fma`, `__ldcg`/`__stcg`, and the `mu_c`/`mu_e`-style caching (rule 2) all stay untouched.
- **`3D_solver/src/calc_visc_high.f90.fypp`**, **`3D_solver/src/calc_visc_high_internal.f90.fypp`**: apply the rules inside `calc_Ev`, `calc_Fv`, `calc_Gv` (each direction repeats the same pattern, x/y/z-permuted; apply rule 1 uniformly even though the current diff is inconsistent about which of `mu4`/`T4`/`qc24` it happened to scalarize in a given direction/order combination — e.g. `calc_Ev`'s `VISC_ORDER==4` branch left `mu4(:)`/`T4(:)` as vectors but scalarized `qc24`, while `calc_Gv`'s equivalent branch scalarized all four).
  - `VISC_ORDER == 4` branch: revert `mu4(:)`, `mut4(:)`, `T4(:)`, `qc24(:)` to vector-slice form per rule 1.
  - `VISC_STENCIL == 'ME4Base'` branch: leave the `mum2..mup3`/`Tm2..Tp3`/`mutm2..mutp3` scalar decomposition and `fma`-based `mu3`/`mut3`/`kTx3` (etc.) exactly as they are (rule 2); only strip the dead `!`-commented formulas above them (rule 3). Revert `qc24(:)`/`qc26(:)` there (used only in the plain-arithmetic `H(:)` expression, no `fma`, no reuse) to vector-slice form per rule 1.
  - Default 6-point-stencil branch: revert `mu6(:)`, `mut6(:)`, `T6(:)`, `qc26(:)` to vector-slice form per rule 1.
  - `calc_visc_high.f90.fypp`-only boundary-fallback `else` block (this 2nd-order-style fallback near boundaries doesn't exist in `_internal`, which is interior-only): keep the `mu_c`/`mu_e`/`mu_cjm`/.../`T_c`/`T_e`/`mut_c`/... caching and the `fma`-based `txx`/`tyy` fusion (rule 2); revert only the single-use `qc2_c`/`qc2_e` (or `qc2_n`) scalars in the `H(:)` construction back to a direct slice (`qc2(i:i+1,j,k)` / `qc2(i,j:j+1,k)`), keeping the already-reused `T_c`/`T_e` as the array-literal `(/T_c, T_e/)` piece of that same expression (rule 1 + rule 2 combined).
  - Keep `__ldcg`/`__stcg` wrapping of every `E`/`F`/`G` store, and `use libm`.
